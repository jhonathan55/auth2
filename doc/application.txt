# CAPA APPLICATION

## Documentacion tecnica en formato Markdown

---

# 1. Proposito

La capa `application` es el coordinador central del sistema de autenticacion. Su responsabilidad es **orquestar los casos de uso** del negocio: recibe datos de entrada tipados mediante DTOs, aplica reglas de negocio invocando exclusivamente contratos del dominio, y devuelve respuestas estructuradas. No conoce Django, HTTP, bases de datos ni servicios de correo de forma directa.

Esta capa actua como el Application Service Layer del patron DDD y como el punto de entrada natural desde cualquier interfaz del sistema hacia el nucleo logico.

---

# 2. Alcance dentro de la arquitectura

## 2.1 Posicion arquitectonica

```text
Interfaces/API  -->  Application  -->  Domain Ports  -->  Infrastructure
                          |
                        DTOs
```

La capa application no depende de la infraestructura directamente. Depende de abstracciones del dominio, que la infraestructura implementa. Esto garantiza que un cambio de base de datos, proveedor de correo o libreria JWT no afecte los casos de uso.

## 2.2 Responsabilidades en este proyecto

- Implementar los tres casos de uso de autenticacion: registro, login y verificacion MFA.
- Transportar datos entre capas mediante DTOs inmutables.
- Elevar excepciones del dominio para representar fallos funcionales.
- Retornar `AuthResponseDTO` como contrato de respuesta unico hacia las interfaces.

# 4. Data Transfer Objects (DTOs)

Los DTOs son `dataclass(frozen=True)` que representan entradas y salidas de los casos de uso. Son inmutables por diseno para evitar mutaciones accidentales entre capas.

## 4.1 LoginDTO

Transporta las credenciales de inicio de sesion.

| Campo | Tipo | Descripcion |
|---|---|---|
| `email` | `str` | Identificador de login |
| `password` | `str` | Contrasena en texto plano |

## 4.2 RegisterDTO

Transporta los datos de un nuevo usuario.

| Campo | Tipo | Descripcion |
|---|---|---|
| `nombres` | `str` | Nombres del usuario |
| `apellidos` | `str` | Apellidos del usuario |
| `email` | `str` | Email unico de registro |
| `password` | `str` | Contrasena en texto plano |

## 4.3 VerifyMFADTO

Transporta el codigo MFA ingresado por el usuario junto al proposito del desafio.

| Campo | Tipo | Descripcion |
|---|---|---|
| `email` | `str` | Email del usuario que verifica |
| `code` | `str` | Codigo MFA recibido |
| `purpose` | `str` | Proposito del desafio, default `LOGIN` |

## 4.4 AuthResponseDTO y AuthUserDTO

`AuthResponseDTO` es la unica estructura de respuesta de los casos de uso hacia las interfaces.

| Campo | Tipo | Descripcion |
|---|---|---|
| `message` | `str` | Mensaje descriptivo del resultado |
| `mfa_required` | `bool` | Indica si se requiere verificacion de segundo factor |
| `access_token` | `str | None` | JWT de acceso, presente si la autenticacion es completa |
| `refresh_token` | `str | None` | JWT de refresco |
| `email` | `str | None` | Email del usuario, presente cuando se espera MFA |
| `user` | `AuthUserDTO | None` | Datos basicos del usuario autenticado |

`AuthUserDTO` encapsula la representacion minima del usuario en respuestas exitosas.

| Campo | Tipo | Descripcion |
|---|---|---|
| `id` | `int` | Identificador del usuario |
| `email` | `str` | Email |
| `nombres` | `str` | Nombres |
| `apellidos` | `str` | Apellidos |
| `roles` | `list[str]` | Lista de roles asignados |

# 5. Casos de uso

## 5.1 RegisterUserUseCase

**Dependencias inyectadas:**

- `UserRepository`
- `PasswordHasher`

**Flujo:**

1. Busca si el email ya existe via `UserRepository.find_by_email`.
2. Si existe, lanza `ValueError`.
3. Construye `UserEntity` con la contrasena hasheada y valores iniciales seguros.
4. Persiste la entidad via `UserRepository.save`.
5. Retorna la entidad persistida.

**Invariantes que aplica:**

- Un email no puede registrarse dos veces.
- La contrasena nunca se almacena en claro.
- Un usuario nuevo inicia con `is_active=True`, `is_staff=False`, `is_email_verified=False`, `mfa_enabled=False`.

## 5.2 LoginUserUseCase

**Dependencias inyectadas:**

- `UserRepository`
- `PasswordHasher`
- `MFARepository`
- `NotificationService`
- `TokenProvider`

**Flujo — sin MFA:**

1. Busca el usuario por email.
2. Verifica contrasena con `PasswordHasher.verify`.
3. Verifica que el usuario este activo.
4. Actualiza `last_login_at`.
5. Genera `access_token` y `refresh_token`.
6. Retorna `AuthResponseDTO` con tokens y datos del usuario.

**Flujo — con MFA habilitado:**

1. Pasos 1 a 4 identicos.
2. Envia el codigo MFA via `NotificationService.send_mfa_code`.
3. Retorna `AuthResponseDTO` con `mfa_required=True` y el email del usuario.

**Invariantes que aplica:**

- Si el usuario no existe o la contrasena es incorrecta, el mensaje de error es identico para evitar enumeracion de usuarios.
- Un usuario inactivo no puede continuar aunque la contrasena sea correcta.

## 5.3 VerifyMFAUseCase

**Dependencias inyectadas:**

- `UserRepository`
- `MFARepository`
- `PasswordHasher`
- `TokenProvider`

**Flujo:**

1. Busca el usuario por email.
2. Busca el desafio activo por `user_id` y `purpose` via `MFARepository`.
3. Valida que el desafio no este consumido.
4. Valida que el desafio no haya expirado.
5. Valida que no se hayan superado los intentos maximos.
6. Incrementa `challenge.attempts`.
7. Verifica el codigo contra `code_hash` con `PasswordHasher.verify`.
8. Si el codigo es incorrecto, persiste el intento y lanza excepcion.
9. Si el codigo es correcto, marca `consumed_at`, genera tokens y retorna `AuthResponseDTO`.

**Invariantes que aplica:**

- Un desafio consumido no puede reutilizarse.
- Un desafio expirado es rechazado aunque el codigo sea valido.
- Cada intento fallido se registra en `challenge.attempts`.
- El codigo se valida como hash, nunca en texto plano.

# 6. Excepciones del dominio usadas por application

| Excepcion | Caso de uso | Condicion |
|---|---|---|
| `InvalidCredentialsException` | Login | Usuario no existe o contrasena incorrecta |
| `InactiveUserException` | Login | `user.is_active == False` |
| `UserNotFoundException` | VerifyMFA | Usuario no existe al verificar |
| `MFAChallengeNotFoundException` | VerifyMFA | No existe desafio activo |
| `InvalidOrExpiredMFACodeException` | VerifyMFA | Desafio consumido, expirado o codigo invalido |
| `MFAAttemptsExceededException` | VerifyMFA | `attempts >= max_attempts` |
| `ValueError` | Register | Email ya registrado |

## 10.2 Secuencia detallada de login

```mermaid
sequenceDiagram
    actor Cliente
    participant LoginUC as LoginUserUseCase
    participant UserRepo as UserRepository
    participant Hasher as PasswordHasher
    participant Notifier as NotificationService
    participant Tokens as TokenProvider

                    LoginUC->>Tokens: generate_access_token(user.id, email, roles)
                    LoginUC->>Tokens: generate_refresh_token(user.id)
                    LoginUC-->>Cliente: AuthResponseDTO(access_token, refresh_token, user)
                end
            end
        end
    end
```

## 10.3 Secuencia detallada de verificacion MFA

```mermaid
sequenceDiagram
    actor Cliente
    participant VerifyUC as VerifyMFAUseCase
    participant UserRepo as UserRepository
    participant MFARepo as MFARepository
    participant Hasher as PasswordHasher
    participant Tokens as TokenProvider

    Cliente->>VerifyUC: execute(VerifyMFADTO)
    VerifyUC->>UserRepo: find_by_email(dto.email)
    UserRepo-->>VerifyUC: User | None

    alt Usuario no existe
        VerifyUC-->>Cliente: UserNotFoundException
    else Usuario existe
        VerifyUC->>MFARepo: find_active_by_user_and_purpose(user.id, dto.purpose)
        MFARepo-->>VerifyUC: MFAChallenge | None

        alt No existe desafio activo
            VerifyUC-->>Cliente: MFAChallengeNotFoundException
        else Desafio encontrado
            alt consumed_at no es None
                VerifyUC-->>Cliente: InvalidOrExpiredMFACodeException
            else expires_at < now
                VerifyUC-->>Cliente: InvalidOrExpiredMFACodeException
            else attempts >= max_attempts
                VerifyUC-->>Cliente: MFAAttemptsExceededException
            else Desafio vigente
                VerifyUC->>Hasher: verify(dto.code, challenge.code_hash)
                Hasher-->>VerifyUC: bool

                alt Codigo invalido
                    VerifyUC->>MFARepo: update(attempts + 1)
                    VerifyUC-->>Cliente: InvalidOrExpiredMFACodeException
                else Codigo valido
                    VerifyUC->>MFARepo: update(consumed_at = now, attempts)
                    VerifyUC->>Tokens: generate_access_token(user.id, email, roles)
                    VerifyUC->>Tokens: generate_refresh_token(user.id)
                    VerifyUC-->>Cliente: AuthResponseDTO(tokens, user)
                end
            end
        end
    end
```

# 11. Inyeccion de dependencias

Los casos de uso reciben todas sus dependencias por constructor. El contenedor de infraestructura (`Container`) resuelve las implementaciones concretas.

```text
Container
├── register_user_use_case()
│   ├── DjangoUserRepository  ->  UserRepository
│   └── DjangoPasswordHasher  ->  PasswordHasher
│
├── login_user_use_case()
│   ├── DjangoUserRepository  ->  UserRepository
│   ├── DjangoPasswordHasher  ->  PasswordHasher
│   ├── DjangoMFARepository   ->  MFARepository
│   ├── EmailNotificationService -> NotificationService
│   └── JwtTokenProvider      ->  TokenProvider
│
└── verify_mfa_use_case()
    ├── DjangoUserRepository  ->  UserRepository
    ├── DjangoMFARepository   ->  MFARepository
    ├── DjangoPasswordHasher  ->  PasswordHasher
    └── JwtTokenProvider      ->  TokenProvider
```

Esto garantiza que los casos de uso son completamente testeables con mocks sin necesidad de levantar Django ni base de datos.

# 12. Seguridad aplicada (OWASP)

## 12.1 Controles presentes

| Control | Implementacion | Riesgo mitigado |
|---|---|---|
| Mensaje de error identico para usuario/password invalidos | `InvalidCredentialsException` con mismo mensaje | User enumeration (OWASP A07) |
| Verificacion de cuenta activa tras validar credenciales | `InactiveUserException` separada | Acceso no autorizado |
| Hashing de contrasenas | `PasswordHasher.hash/verify` | Exposicion de credenciales (OWASP A02) |
| MFA de segundo factor | `send_mfa_code` + `VerifyMFAUseCase` | Credential stuffing / brute force (OWASP A07) |
| Limite de intentos MFA | `max_attempts` en `MFAChallenge` | Brute force sobre codigo temporal |
| Expiracion de desafio MFA | `expires_at` verificado en use case | Replay attacks sobre codigos caducados |
| Marcado de consumo en desafio | `consumed_at` | Reutilizacion de codigo MFA |
| Tokens con expiracion corta | `exp` en JWT, 1h access / 7d refresh | Secuestro de sesion prolongado |
| No logear contrasenas ni codigos | Logs solo incluyen email, user_id, eventos | Data leakage (OWASP A09) |

# 13. Observaciones de diseno del estado actual

## 13.1 LoginUserUseCase no persiste el desafio MFA

El `LoginUserUseCase` envia un codigo fijo por correo sin crear ni guardar un `MFAChallenge` en base de datos. El `VerifyMFAUseCase` espera encontrar ese desafio mediante `MFARepository`. El flujo MFA no esta operativamente completo todavia.

## 13.2 RegisterUserUseCase recibe parametros sueltos, no un DTO

A diferencia de `LoginUserUseCase` y `VerifyMFAUseCase`, `RegisterUserUseCase.execute` acepta cuatro parametros posicionales en lugar de recibir un `RegisterDTO`. Esto crea inconsistencia en el contrato de los casos de uso.

## 13.3 LoginResult es un dataclass no utilizado

`LoginResult` esta definido en `login_user.py` pero no se usa en ningun lugar del flujo actual. El caso de uso retorna `AuthResponseDTO` directamente.

# 14. Recomendaciones de evolucion

## 14.1 Completar el flujo MFA en login

El `LoginUserUseCase` deberia:

1. Generar un codigo aleatorio criptograficamente seguro.
2. Hashearlo con `PasswordHasher.hash`.
3. Construir un `MFAChallenge` con `uuid4`, `purpose=LOGIN`, `channel=EMAIL`, y duracion de 5 minutos.
4. Persistirlo via `MFARepository.save`.
5. Enviar el codigo plano por `NotificationService.send_mfa_code`.

## 14.2 Unificar el contrato de entrada de RegisterUserUseCase

Adoptar `RegisterDTO` como parametro del metodo `execute` para mantener coherencia con los demas casos de uso.

## 14.3 Eliminar LoginResult

Al no estar en uso, `LoginResult` debe eliminarse para reducir ruido y confusion en el modulo.

# 15. Resumen ejecutivo

La capa `application` tiene una separacion de responsabilidades correcta y es testeable mediante inyeccion de dependencias. Los flujos de registro, login sin MFA y verificacion MFA estan bien implementados funcionalmente, con manejo explicito de todas las ramas de error del dominio. Las oportunidades de mejora mas relevantes son: completar la implementacion del login con MFA para que persista el desafio antes de enviarlo, uniformizar el contrato de entrada de `RegisterUserUseCase` y eliminar el artefacto no utilizado `LoginResult`.
